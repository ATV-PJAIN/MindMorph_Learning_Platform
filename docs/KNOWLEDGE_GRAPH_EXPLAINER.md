# How the Knowledge Graph Works in MindMorph

> Historical design explanation. Current P1 #7 uses saved sessions as the authority and writes
> session-owned Neo4j mirrors; fresh grounded paths bypass shared roadmap caches. Neo4j is not a
> lesson/exercise bank. See [GROUNDING.md](GROUNDING.md) and
> [NEO4J_ARCHITECTURE.md](NEO4J_ARCHITECTURE.md) for current behavior.

> This document explains only the knowledge graph —
> what it is, how it is built, how the rest of the app uses it,
> and what changes if you move it into a dedicated graph database.

---

## 1. What the Knowledge Graph Is

When a user asks *"I want to learn machine learning"*, MindMorph does not give them
a flat list of topics. It builds a **Skill Dependency Graph** — a map of skills
where each skill knows what you must learn *before* it.

It looks like this conceptually:

```
  [Linear Algebra] ─────────────────────────────────▶ [ML Fundamentals]
  [Python Basics]  ───────────────────────────────▶ [ML Fundamentals]
                                                             │
                                                        ▼         ▼
                                              [Supervised]   [Unsupervised]
                                                   │
                                                   ▼
                                          [Model Evaluation]
                                                   │
                                                   ▼
                                            [Deep Learning]
```

Each box is a **node** (a skill). Each arrow is an **edge** (a dependency — "you need
this before that"). This is a **directed acyclic graph** — it has direction (arrows) and
no cycles (you cannot be a prerequisite of your own prerequisite).

### What each node actually holds (from `skill_graph_schema.py`)

```python
class SkillNode:
    id          = "ml_fundamentals"       # stable identifier used internally
    label       = "ML Fundamentals"       # shown to the user
    description = "Core concepts of..."   # one-sentence explanation
    level       = "intermediate"          # foundational | intermediate | advanced
```

### What each edge holds

```python
class SkillEdge:
    source   = "python_basics"    # the prerequisite
    target   = "ml_fundamentals"  # what depends on it
    relation = "prerequisite"     # always this for now
```

The full graph is a `SkillGraph` with a `summary`, a list of `nodes`, and a list of `edges`.

## 2. How the Graph Is Built

The graph is not hard-coded. It is **generated by the LLM pipeline every time** a user
submits a new learning goal. Here is the exact sequence:

```
User: "teach me machine learning"
         │
         ▼
  1. Orchestrator  → decides this is a SCOUT (learning plan) request
         │
         ▼
  2. Scout Agent   → splits the query into three specialist questions:
                     "What are the academic prerequisites for ML?"
                     "What ML skills are in demand in the job market?"
                     "What real projects should someone build to learn ML?"
         │
         ├─────────────────────────────────────────────┐
         ▼                      ▼                      ▼
  3. Academic Agent    Market Agent           Practical Agent
     (reads papers,    (searches job          (finds GitHub repos,
      curricula)        postings)              real-world usage)
         │                      │                      │
         └──────────────────────┴──────────────────────┘
                                │
                                ▼
  4. Consensus Agent  → takes ALL THREE perspectives, reconciles them,
                        and asks the LLM to output a structured SkillGraph JSON
                                │
                                ▼
  5. Reviewer Agent   → checks the graph for logical consistency
                                │
                                ▼
  6. skill_graph_render.py → converts the JSON graph into a Mermaid flowchart
                              (the visual diagram shown in the frontend)
```

The Consensus agent is the heart of it. It calls the LLM with this input:

```python
# From consensus_agent.py
"""
Learning goal: {user_query}

ACADEMIC perspective:  {academic_output}
MARKET perspective:    {market_output}
PRACTICAL perspective: {practical_output}

Reconcile these into a Skill Dependency Graph.
"""
```

The LLM responds with **structured JSON** — a `SkillGraph` validated by Pydantic.
The `prune_dangling_edges()` function in `skill_graph_adapt.py` then runs
a deterministic cleanup pass to remove any edges pointing to skills that don't exist
(LLM hallucination guard), and the result is stored in the session.

## 3. How the Rest of the App Uses the Graph

The graph is not just a diagram. It **drives every other feature** in MindMorph.

### 3.1 The lesson order comes from the graph

The prerequisite edges define the order in which lessons are unlocked. A skill whose
prerequisites are not yet mastered is **locked** — the user cannot jump ahead.

The completion service reads the edges to compute which nodes are currently available
(all prerequisites mastered), in progress, or still locked. This is why the graph is
a **dependency graph** and not just a list — the edges enforce the learning sequence
automatically.

### 3.2 Exercises are generated per node

When a user reaches a skill node, the Exercise graph (`graph/exercise_graph.py`) is
invoked for that specific node. The exercise is generated based on:
- What that skill node covers (its `label` and `description`)
- What the user has already mastered (context from completed prerequisite nodes)

The exercise result (pass/fail score) is stored back against that **node ID** in the
user's session as `node_state[node_id].mastery_score`.

### 3.3 The visual diagram is the graph rendered

`skill_graph_render.py` takes the same `{nodes, edges}` dict and converts it to a
**Mermaid flowchart** string. The frontend renders this as the interactive diagram
the user sees. The colour of each node (blue = foundational, yellow = intermediate,
red = advanced) comes directly from the `level` field on each `SkillNode`.

The mastery overlay (✅ mastered, 🔒 blocked, ▶ in progress) is added on top by
passing `node_state` to `skill_graph_to_mermaid()`.

### 3.4 Adaptive learning modifies the graph

When a user scores below 40 on an exercise, the Adaptation agent
(`graph/skill_graph_adapt.py`) proposes **new remedial nodes** to add to the graph.

```python
# apply_adaptation() in skill_graph_adapt.py
# - Adds new prerequisite sub-skills to help the user fill the gap
# - NEVER removes or renames existing nodes (mastery state is keyed on node_id)
# - NEVER creates duplicate nodes
# - If the new node has no path to the struggling skill, one is synthesized
```

So the graph is **not static** — it grows as the learner struggles.

## 4. Where the Graph Lives Right Now

Currently the entire `SkillGraph` JSON is stored as part of a large `learning_session`
blob in a single Postgres JSONB column:

```python
# persistence/models.py → LearningSessionRow
data: dict  # the whole session: skill_graph + node_state + lessons + mastery scores
```

The key in that dict is `session["skill_graph"]`. Every read or write of
any single skill's mastery score requires loading and re-saving this **entire blob**.

---

## 5. What Is Missing Right Now

### Problem 1 — The graph is recreated for every user

If 100 users ask "teach me Python", the pipeline runs 100 times and produces
100 near-identical graphs, stored in 100 separate JSONB blobs.
The graph itself is **not shared** between users.

### Problem 2 — You cannot query the graph — only load it

To answer "what skills must I complete before I can reach Deep Learning?", the code
loads the full blob and runs a Python DFS (`_reaches()` in `skill_graph_adapt.py`).
There is no way to ask the database itself this question because the graph
is not *in* a graph database — it is a dict sitting in Postgres.

### Problem 3 — Updating one skill requires rewriting everything

When a user masters `python_basics`, the code updates `node_state["python_basics"]`
and then **saves the entire session blob again**. At scale with large graphs this
becomes an expensive full write every time any node changes.

## 6. What Changes If You Move the Graph into a Graph Database

This section is the direct answer to *"if I implement this, what effect does it make?"*

### Before (current state)

```
User A asks "teach me Python"
  → 6-agent pipeline runs → SkillGraph JSON produced
  → stored as blob in user_A's Postgres row

User B asks "teach me Python"
  → 6-agent pipeline runs AGAIN → same SkillGraph JSON produced
  → stored as blob in user_B's Postgres row

Result:
  - Two identical graphs in two separate blobs
  - Pipeline ran twice for the same knowledge
  - Updating mastery for User A = full blob rewrite
  - "What must I learn before X?" = load blob → Python DFS
```

### After (with a graph database, e.g. Neo4j)

```
User A asks "teach me Python"
  → Check graph DB: does (:Topic {canonical:"python"}) exist? → NO
  → 6-agent pipeline runs → SkillGraph JSON produced
  → WRITE as real graph nodes and edges into the graph DB:
      (:Skill {id:"python_basics", level:"foundational"})
      (:Skill {id:"oop",           level:"intermediate"})
      (:Skill {id:"python_basics"}) ──[:PREREQUISITE]──▶ (:Skill {id:"oop"})

User B asks "teach me Python"
  → Check graph DB: does (:Topic {canonical:"python"}) exist? → YES
  → Return the existing graph nodes/edges DIRECTLY from the DB
  → 6-agent pipeline is SKIPPED entirely
  → User B's progress is stored separately:
      (:Progress {user:"B", skill:"python_basics", score:0.0})

Result:
  - ONE graph in the DB, shared by all users
  - Pipeline runs ONCE per topic, not once per user
  - Updating mastery for User A = update ONE property on ONE node
  - "What must I learn before Deep Learning?" = one Cypher query:
      MATCH (prereq)-[:PREREQUISITE*]->(:Skill {id:"deep_learning"})
      RETURN prereq.label
```

### Concrete effect on each feature

| Feature | Before — JSONB blob | After — Graph DB |
|---|---|---|
| **Lesson order** | Python DFS on loaded blob | Native graph traversal query |
| **Exercise generation** | Context loaded from full blob | Node properties fetched directly |
| **Mastery update** | Full blob rewrite | Set one property on one node |
| **Visual diagram** | Render from loaded blob | Render from queried nodes/edges |
| **Adaptive new nodes** | Rebuild dict, save full blob | `MERGE (:Skill)` + `CREATE edge` |
| **Same topic, new user** | Full pipeline re-run | Return existing graph, skip pipeline |
| **"What comes before X?"** | Python DFS in `_reaches()` | `MATCH ()-[:PREREQUISITE*]->()` |
| **Graph grows (adaptation)** | Full blob rewrite | Atomic node + edge addition |

---

## 7. What Does NOT Change

These parts of MindMorph are **completely unaffected** regardless of whether you use
a graph database:

- The **agent pipeline** (`learning_plan_graph.py`) — still runs on a cache miss
- The **Consensus agent** — still builds the `SkillGraph` Pydantic object
- The **exercise generation** — still triggered per node
- The **user session** in Postgres — still stores user-specific state (progress, history)
- The **frontend** — still receives the same Mermaid diagram string

The graph DB sits **underneath** the existing pipeline, not replacing it.

---

## 8. Summary

The knowledge graph in MindMorph is a directed map of skills where each node is a
skill and each edge is a dependency ("learn A before B"). It is generated by the
Consensus agent, which reconciles academic, market, and practical research into a
structured JSON. That graph then drives every downstream feature — lesson unlocking,
exercise generation, the visual diagram, and adaptive remediation. Right now it lives
as a JSON blob in Postgres, rebuilt from scratch for every user. Moving it into a
graph database means the graph is **built once per topic and shared by everyone**:
new users get the graph instantly, mastery updates become atomic single-node writes,
and prerequisite queries become native database operations instead of Python DFS.

## Grounding regression checks

- Create a path with a relevant native-text PDF, without uploads, and with an unrelated PDF.
  Relevant material may enter evidence; unrelated material must be excluded; every case still has
  a usable goal/profile-based path. Compare actual supplied evidence, not random wording/node counts.
- Upload after creating a path or saving a lesson. Future generation may use it; roadmap, mastery,
  saved exercise/content, revision and practice history remain intact. Reopening reuses saved content.
- Confirm new lesson/practice share one bundle and practice uses taught context. Tutor fresh retrieval
  includes the selected skill; its public query never contains a private passage/question/filename.
- Check page/source/snippet labels, disabled/unavailable/no-match states, historical unknown sources,
  fabricated citations, split streamed references and cancellation/recovery. Check keyboard/mobile
  source disclosure and saved tutor sources after refetch.
- Use `scripts/verify_grounding_storage.py` for disposable migration/isolation/restart/outage,
  atomic graph rollback/stale revision and 100,000-passage/ten-search capacity evidence. Never point
  destructive legacy graph tests at an application database. Do not substitute table creation for migrations.
- Use `scripts/evaluate_grounding.py` for labelled real local-model samples and
  `scripts/smoke_grounding.py` for synthetic live configured-generation checks. The latter uses
  short Boost lessons with the optional rich-content tail off and deliberately unavailable market
  scraping to bound calls; it does not change production defaults or the running app's data.

## 1. What this product does (one-paragraph orientation)

MindMorph turns a learning goal (e.g. *"I want to learn Python for data science"*) into an
**interactive skill roadmap**. A team of LLM agents researches the goal, builds a **skill dependency
graph**, and lets the learner click any skill to get a **lesson** (teaching content + a practice
exercise). The learner's exercise is **graded live**, the score **updates mastery** on the graph, and
a low score **adapts the graph** — adding remedial prerequisite skills and regenerating the lesson to
target the learner's gaps. Two other routes exist (a standalone lesson, a standalone exercise) — the
Orchestrator answers those queries directly instead of building a path, and the dashboard says so
rather than navigating anywhere.

**A note on non-determinism:** all content, lessons, and exercises are **generated by an LLM at
runtime**. The same query will produce different wording, different exercises, and different unit
tests on each run. Test cases below therefore assert on **structure and behavior** (a graph appears,
a node turns green, a remedial node is added) — **not** on exact text. Where an exercise must be
solved, read the generated unit tests out of the session payload to see what is required (the lesson
panel shows the statement and the editor, not the tests), then use the recipes in **Appendix A**.

## 2. Scope

### In scope (implemented — test these)
| Area | Feature |
|---|---|
| **SCOUT** route | Skill dependency graph generation, reviewer verdict, specialist outputs (Academic / Market / Practical) |
| **Adaptive learning loop** | Skill graph as the node picker, composed lesson (content + exercise), lesson caching, live grading, mastery capture, graph adaptation (remedial nodes / unlock edges), score-aware regeneration, sticky mastery |
| **CONTENT** route | Standalone "quick lesson" (dual-path: creative + live web grounding) — answered directly, no path created |
| **EXERCISE** route | Standalone exercise — answered directly, no path created |
| **Persistence & grounding** | Postgres session store (JSONB rows, `DATABASE_URL`; `MINDMORPH_STORE=memory` is the zero-infra opt-out, not the default) + opt-in local RAG / vector search (`MINDMORPH_RAG=1`, `rag/`, pgvector) |
| Cross-cutting | Logging, error handling, LLM provider selection (keyless Ollama path, Groq key-pool rotation, fallback) |
| Automated tests | `pytest` suite |

### Out of scope (not implemented — do **not** raise bugs for these)
Real authentication (the email field on the login gate is MVP identity only — no password, no
session token, no account records), multi-**vendor** model routing (GPT / Claude / Gemini / Bedrock —
the two backends that do exist, Groq and Ollama, are in scope), Redis / S3 / Kafka, containerized
grading sandbox, real dataset ingestion (dataset exercises return links), deployment / CI / K8s,
telemetry **pipelines** — no metrics backend, exporter or dashboard exists. Note the narrower carve-out:
per-stage token/cost accounting and wall-clock latency spans *are* recorded in-process (`services/cost.py`,
`services/timing.py`), log as `timing: <stage> <ms> ms`, and ride the session payload
(`learning_session.timing`, `lessons.<node>.timing`) — so a **missing or empty** `timing` block on a
completed graph build or lesson compose **is** in scope. See `docs/IMPLEMENTATION_STATUS.md` for the full
roadmap.

## 3. Test environment & setup

### 3.1 Prerequisites
- macOS or Linux, **Anaconda/Miniconda** installed.
- A **`conda` env named `mindmorph`** (the project's required env).
- **[Ollama](https://ollama.com) installed and running** (`http://localhost:11434`) with both tier
  models pulled — `ollama pull qwen2.5:7b` and `ollama pull qwen2.5:14b`. This is the default backend
  and the only one that needs no account.
- API keys — **all optional**; there is no mandatory secret:
  - `GROQ_API_KEYS` — *optional*, **plural**, comma-separated **pool** of Groq keys. Present ⇒ hosted
    Groq (`openai/gpt-oss-120b`) runs in front of Ollama and is much faster. Absent/empty ⇒ everything
    runs on local Ollama; `config.py` raises nothing.
  - `APIFY_API_TOKEN` — *optional*; only the **Market** tab / Market agent needs it. Its absence is
    expected to degrade gracefully (no crash).
  - `GITHUB_TOKEN` — *optional*; improves the Practical agent's GitHub results.

> **Speed expectation:** on the keyless Ollama path inference is slow — a full skill-graph build takes
> **minutes** on `qwen2.5:14b`. Slowness on Ollama is **not** a bug; only raise a timeout defect when
> Groq keys are configured. Test Suites B–G on the Groq path if you have keys.

### 3.2 One-time setup
```bash
# from the project root
git checkout main && git pull
conda run -n mindmorph pip install -r requirements.txt   # if env not already provisioned
```
A `.env` file in the project root is **optional** — with no `.env` at all the app runs on Ollama. To
test the hosted path, create one:
```
GROQ_API_KEYS=<key1>,<key2>,<key3>   # optional pool; unset/empty = Ollama-only
APIFY_API_TOKEN=<optional key>
GITHUB_TOKEN=<optional token>
```

### 3.3 Launch the app
```bash
# Backend (FastAPI). Default store is Postgres — start it first: docker compose up -d db
conda run -n mindmorph uvicorn api.main:app --port 8000
# ...or run with no infra at all (sessions won't survive an API restart):
# MINDMORPH_STORE=memory conda run -n mindmorph uvicorn api.main:app --port 8000
# Frontend (Next.js), separate terminal
cd web && npm install && npm run dev
```
Open **http://localhost:3000** (API on :8000). `web/.env.local` must set
`NEXT_PUBLIC_API_URL=http://localhost:8000`. Backend runtime logs print to the uvicorn terminal and
`logs/mindmorph.log`. (The legacy Streamlit app was retired in P3 #12.)

### 3.4 Run the automated test suite (separate terminal)
```bash
conda run -n mindmorph python -m pytest -q
```

## 4. How the three "routes" work (important for testers)

Everything starts from the same **Start a new path** box on the dashboard. An Orchestrator agent reads
your query and routes it to one of three flows. Phrase the query to force the route you want to test:

| Route | Triggered by (intent) | Example queries |
|---|---|---|
| **SCOUT** (full roadmap + adaptive loop) | "I want to learn / teach me / roadmap for …" | `I want to learn Python for data science` · `Teach me machine learning` |
| **CONTENT** (one quick lesson) | "Explain / give me a lesson on / what is …" | `Explain Python list comprehensions` · `Give me a quick lesson on REST APIs` |
| **EXERCISE** (one standalone exercise) | "Give me an exercise / a coding challenge on …" | `Give me a coding exercise on Python loops` |

Only **SCOUT** produces a session to navigate to. CONTENT and EXERCISE return their answer on the
`/sessions/stream` response with no `session_id`, so the dashboard stays put and shows an **"Answered
directly"** notice instead (`web/app/page.tsx`). Their generated content is in the response payload,
not on screen — Suites D and E therefore read it from the API.

> Routing is LLM-driven. If a query lands on the wrong route, rephrase using the cues above. A
> mis-route on an ambiguous query is **low severity**, not a blocker.

> **Status glyphs reference** (`web/lib/status.ts` `STATUS_STYLE`): **✓ Complete** · **🔒 Locked**
> (prerequisites pending, or a sub-40 grade's remediation lock) · **◐ Keep practicing** (40–79) ·
> **↻ Needs review** (< 40) · **○ Available**. A node earns **✓ Complete only when it AND all its
> prerequisites (transitively) are mastered**; a node that passed its own exercise (score ≥ 80) but
> still has an incomplete prerequisite shows **🔒**. Thresholds are Python-side and single-sourced in
> `services/mastery.py` (`MASTERY_THRESHOLD=80`, `REVIEW_THRESHOLD=40`, `REMEDIATION_THRESHOLD=40`).
> Per-exercise score→band on a 5-test exercise: 5/5 or 4/5 → mastered, 3/5 or 2/5 → ◐, ≤1/5 → sub-40
> (lock + remediation). The `N/M` header counts **fully-complete** nodes.

## 6. Cross-cutting checks

- **Logging:** terminal + `logs/mindmorph.log` should show structured lines for each stage, e.g.
  `service: astream_session (query=…)`, `service: composing lesson for node <id>`,
  `service: lesson <id> HIT (cache_hits=N)`, `service: grading <format> submission for node <id>`,
  `service: adapting graph after grade on node <id> (score=…)`,
  `Adaptation: +N node(s) +M edge(s)…`, `ContentAgent: generating … (remediation=True)`. LLM provider
  events use the `llm:` prefix — `llm: key N/M failed with HTTP 429 … rotating to next key` (WARNING),
  `llm: all N keys exhausted — falling back` (WARNING), `llm: key N/M failed permanently with HTTP 404
  — NOT rotating, falling back` (ERROR). No secrets (API keys) should ever appear in logs — key
  positions are logged as `key 2/3`, never the key value.
- **Latency lines:** every LLM-backed stage emits `timing: <stage> <ms> ms` — `graph.orchestrator`,
  `graph.scout`, the three specialists, `graph.consensus`, `graph.reviewer`, `graph.total`,
  `lesson.content`, `lesson.exercise`, `lesson.total`, and the grade spans. These are informational; a
  *missing* line for a stage that demonstrably ran is the defect, not a slow one.
- **Degraded-grounding lines (new — these are expected, not defects).** The pipeline used to fail open
  silently; each degradation now says so at WARNING. Seeing one means that arm was unavailable, which is
  usually just a missing optional token: `Consensus degraded: no MARKET grounding for …` (no
  `APIFY_API_TOKEN`, or the scrape returned nothing); `GitHub grounding unavailable:
  GITHUB_PERSONAL_TOKEN is not set` / `GitHub grounding empty: no repositories returned for …`;
  `Consensus graph incoherent for …: dropped N edge(s) referencing unknown node ids: …`;
  `Reviewer REJECTED the skill graph for … (serving it anyway): …`. The **absence** of any such line on a
  visibly incomplete result is the more interesting defect. Note the last two: a rejected review does
  **not** block the session (there is no retry loop), and a dropped dangling edge is a deliberate repair.
- **Security note (do not "fix" as a bug):** code grading runs the learner's Python in a subprocess
  with a wall-clock timeout and secret-scrubbed env. It is a **hang-guard for a local single-user
  prototype, not a security sandbox** (documented in `tools/code_executor.py`). Real isolation is a
  future hosted-deployment item. Do **not** run hostile code against a shared/production host.

## Appendix A — Exercise solution recipes

Exercises are LLM-generated, so the **function name, signature, and unit tests differ every run**.
The reliable procedure:

1. Fetch the tests. They are **not** shown in the lesson panel — read
   `learning_session.lessons.<node_id>.exercise.grading_artifact.unit_tests` from
   `GET /sessions/<user>/<session>` (curl, or the devtools network tab on the lesson request). Read
   `from solution import <NAME>` and each `def test_…` assert.
2. Your editor content = the full `solution.py`. Define `<NAME>` to match.
3. Pick the outcome you want to test:

**CORRECT (→ 100% → ✓ Complete):** implement `<NAME>` so every assert passes. Watch for edge cases
the tests demand — e.g. raising `ValueError` on negative input, **with the exact message** the test
checks (`assert str(e) == '…'`).

**WRONG (→ 0% → `needs_review` + remediation lock, displays 🔒):** define the name but return a value
that fails every assert. Universal:
```python
def <NAME>(*args, **kwargs):
    return None
```

**PARTIAL (→ 40–79% → ◐ Keep practicing):** implement the core logic correctly but skip the
edge/validation cases, so some tests pass and some fail. Then **read `passed/total`** and tune:
- landed ≥ 80% → break one more case;
- landed < 40% → fix one case.

**Worked example.** For a harness like:
```python
from solution import calculate_rectangle_properties
def test_normal():            # (5,3) -> {'area':15,'perimeter':16}
def test_zero_length():       # (0,3) -> {'area':0,'perimeter':6}
def test_negative_length():   # (-5,3) -> raises ValueError('Length and width must be non-negative')
```
- Correct (100%):
  ```python
  def calculate_rectangle_properties(length, width):
      if length < 0 or width < 0:
          raise ValueError('Length and width must be non-negative')
      return {'area': length * width, 'perimeter': 2 * (length + width)}
  ```
- Partial (passes the positive/zero tests, fails the negative ones):
  ```python
  def calculate_rectangle_properties(length, width):
      return {'area': length * width, 'perimeter': 2 * (length + width)}
  ```
- Wrong (0%):
  ```python
  def calculate_rectangle_properties(length, width):
      return {}
  ```

> Tip: the worked-example numbers printed in the **statement** are sometimes themselves
> LLM-miscalculated. Trust the **unit tests in `grading_artifact`**, not the prose examples.
